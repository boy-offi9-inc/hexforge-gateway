# Unit/integration tests

Run with `npm test` (single run) or `npm run test:watch`. These are plain
[Vitest](https://vitest.dev) tests - no live Gateway instance needed, unlike
`scripts/smoke-test.sh`, which they complement rather than replace:

|                         | covers                                                | needs                                              |
| ----------------------- | ----------------------------------------------------- | -------------------------------------------------- |
| `scripts/smoke-test.sh` | end-to-end happy paths through a real running Gateway | a live instance (CI starts one)                    |
| `tests/*.test.ts`       | retry/failure logic, concurrency, edge cases          | nothing - pure unit tests with mocked dependencies |

## What's covered so far

- **`job-engine.test.ts`** - JobEngine's retry logic: succeeds first try,
  retries then succeeds, exhausts `maxAttempts` and fails, and a
  regression test for the fast-fail race (a task that's already terminal
  by the time `dispatch()` resolves must resolve synchronously via
  `getTask()`, without a stray event listener left registered).
- **`workflow-engine.test.ts`** - WorkflowEngine's step sequencing: runs
  every step and merges `mergePreviousResult` correctly, stops the whole
  workflow on a step failure without dispatching later steps, and the
  same already-terminal-by-the-time-we-check race as above, one layer up
  (a step's Job, not a Job's Task).
- **`local-storage.provider.test.ts`** - the local JSON file store:
  upsert/get/list/delete/find round-trip correctly, writes actually land
  on disk (not just in the in-memory cache), collections stay independent
  of each other, and - the specific race its own module comment calls
  out - concurrent upserts/deletes on one collection don't clobber each
  other. `upsertRecords` (one read and one write for many records) stores
  and overwrites correctly, writes nothing for an empty list, and is
  serialized with single upserts.
- **`ai-provider.test.ts`** - the AI provider layer, with `fetch` mocked:
  for Anthropic, the shared OpenAI-compatible shape (via Groq, which
  Groq/OpenAI/DeepSeek/xAI/Mistral/openai-compatible all reuse), Gemini,
  and Ollama - each provider's "not configured" error, exact request
  shape (URL, headers, body), successful-response parsing, a non-ok HTTP
  response surfaced with status + body, and a malformed/empty response
  producing a clear error rather than returning garbage. Groq and Ollama
  also cover a network-level `fetch` rejection getting wrapped in a
  friendlier reachability message.
- **`capability-registry.test.ts`** - the capability registry: providers ordered by priority, all of an adapter's operations grouped per capability, fallback when a backend's availability probe says no (or throws), malformed capability ids and duplicate operation names rejected, and replace/unregister. Pure unit test, no mocks - the registry has no dependencies.
- **`builtin-capabilities.test.ts`** - the built-in descriptors are plain data, so this needs no mocks: all eight agents are described and pass registry validation, frida's push/start/stop-server operations group under one capability, and `outputs` is only declared for the operations whose result is a tracked path (`jadx.decompile`, `apktool.decode`, `apktool.build`, `filesystem.scan-secrets`, `frida.trace`).
- **`capability-routes.test.ts`** - `GET /capabilities` on a bare Fastify instance (same approach as `api-routes.test.ts`, without its mocking, since the route only reads the registry singleton): providers come back ordered by priority with their operation names, and the `isAvailable` probe never reaches the JSON.
- **`graph-service.test.ts`** - real local storage in a throwaway `DATA_DIR` next to the real artifact service: an entity created then merged on the same type + name (stable id, attributes overlaid, artifact ids unioned), type and workspace keeping same-named entities apart, unknown or foreign artifacts rejected with nothing saved, listing sorted with the type and name filters; edges idempotent, direction and relation part of identity, self edges and missing or foreign ends rejected, and edge listing by either end; plus `indexBatch`: entities and edges added in one call with created/updated counts, merging into existing ones, repeats within a batch collapsed, and bad batches (foreign artifact, edge end not in the batch, self edge) rejected with nothing written.
- **`java-indexer.test.ts`** - the decompiled-sources indexer: `parseJavaSources` (pure) makes classes, packages with a class count, and `contains` edges, records each class's source file, handles top-level classes, skips non-java files and `package-info`/`module-info`, and flags truncation at the cap; `listFiles` returns sorted relative paths and honours its limit; and `indexJavaArtifact` runs end to end on a real temp directory with real storage - jadx's `sources/` layout (a sibling `resources/` ignored), the flat fallback, and idempotence on a second run.
- **`graph-routes.test.ts`** - the five graph routes on a bare Fastify instance with both services mocked (`GraphError` kept real, since the routes branch on `instanceof`): 201 vs 200 for created vs merged, 400 for bad bodies, attribute shapes and graph errors, 404 for an unknown workspace or entity, and the filters passed through.
- **`finding-service.test.ts`** - real local storage in a throwaway `DATA_DIR` next to the real artifact service, so evidence is checked against artifacts that were actually recorded: a default unverified finding, valid evidence accepted, an unknown artifact or one from another workspace rejected (nothing saved), `confirmed` refused without evidence on create and on update, replaced evidence re-checked and the old evidence kept on failure, per-workspace listing with the status filter, and evidence that cites a graph entity: accepted when the entity was observed in the cited artifact, rejected when it is unknown, from another workspace, or wasn't observed there, re-checked on update, and findings listed by the entity they cite.
- **`finding-verifier.test.ts`** - `parseLocation` (path, `:line`, `:a-b`, a trailing column, colons that aren't line numbers), `summarize` (failed beats everything, partial, unverified for none or empty), and `checkLocation` on a real temp directory: files with and without lines, resolution against the artifact directory then `sources/`, line counting with and without a trailing newline, lines past the end or backwards or zero, missing files, parent paths / absolute paths / a symlink out of the artifact all refused, single-file and missing-directory artifacts left unverified, and the size limit. `verifyFinding` runs against real local storage with a fresh module graph per test: per-item results, the summaries, evidence whose artifact is gone or from another workspace, and a finding with no evidence.
- **`finding-routes.test.ts`** - the four finding routes on a bare Fastify instance with both services mocked (`EvidenceError` kept real, since the routes branch on `instanceof`): 201 create, 400 for a bad body or evidence error, 404 for an unknown workspace or finding, the status and `entityId` filters passed through, PATCH, and `GET /findings/:id/verification` (the report, or 404 without calling the verifier).
- **`task-output.test.ts`** - `withSavedOutput` against a throwaway `WORKSPACES_ROOT` (fresh module graph per test, since config is read at import): the result saved as `<taskId>.json` with `outputPath` added and the file holding the original result, separate files per task so nothing is overwritten, and the unchanged result (plus a warning) when the file can't be written. The agents' scan-secrets and trace handlers themselves aren't unit-tested - they need a worker thread and the frida CLI.
- **`tool-versions.test.ts`** - `createToolVersionResolver` takes its command runner as an argument, so canned output stands in for real tools: versions filled in from the first output line, unprobed or failing backends left without one (never throwing), a declared version kept, a successful probe cached but a failed one retried, and long output capped.
- **`artifact-recorder.test.ts`** - `extractArtifacts` is a pure function (task + registry in, artifact inputs out), so no storage, events or mocks: a directory from `outputDir`, a file from `outputPath`, and nothing for failed tasks, unknown agents, operations declaring no or several outputs, or results without a usable path.
- **`artifact-service.test.ts`** - real local storage in a throwaway `DATA_DIR` with a fresh module graph per test: record/get/list per workspace, the `kind` filter, and updating in place (same id and `createdAt`, new `source`) when the same kind is produced at the same path again, including refreshing the recorded tool versions.
- **`artifact-routes.test.ts`** - `GET /workspaces/:id/artifacts` (kind filter passed through, 404 unknown workspace, 400 empty `kind`) and `GET /artifacts/:artifactId` (200/404), on a bare Fastify instance with both services mocked.
- **`protocol.test.ts`** - the MCP server's shared JSON-RPC dispatch
  (`src/mcp-server/protocol.ts`, used by both the stdio and Streamable
  HTTP transports): `initialize`/`tools/list`/unknown-method handling,
  notifications correctly producing no response, an unknown tool name
  and a missing `tools/call` "name" param each erroring the _right_ way
  and the capability/artifact/graph/finding tools: each reaches the right
  gateway-client function with its filters, `create_finding` always sends
  `source: "ai"` (a caller-supplied `source` is ignored), required ids and
  claims are checked before any call, and a rejected finding comes back as
  an error result carrying the Gateway's reason, and `verify_finding` requires a findingId and returns the Gateway's report without touching workspaces
  (tool result vs. JSON-RPC error - see `docs/MCP_SERVER.md`), a meta
  tool dispatching straight to its `gateway-client.ts` function, an
